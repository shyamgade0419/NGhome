## 8. Plan

Phases are ordered by resident value and by dependency. Each is a complete vertical slice (migration, API, authorization, tests, web and mobile UI) and is committed and verified before the next begins.

| Phase | Scope | Why this order |
|---|---|---|
| 0 | Close O1 (run tenant e2e in CI), O3 (notification idempotency), O4 (stricter limits) | Visitor alerts are unsafe without them. |
| A | Visitor and gate: guard role, resident invitations (time-limited, revocable codes), walk-in registration, approve or reject, check-in/out, logs, policy, audit | The largest gap against MyGate. |
| B | Delivery and domestic help | Reuses Phase A entry and notification machinery. |
| C | Vehicles, parking, staff attendance | Independent of A and B. |
| D | Refunds, reversals and credit notes; reminders; defaulter ageing; polls; SOS; vendors and assets | Financial items need accounting review first; no statutory (GST/TDS) claims without validation. |
| UI | Shared skeleton, empty-state, table and form primitives; resident home re-prioritisation | Runs alongside each phase, applied to the screens it touches. |

### Decisions that affect production and are therefore recorded here

1. **New role `SECURITY_GUARD`.** An additive Postgres enum value (`ALTER TYPE … ADD VALUE`); existing rows are untouched. Guards get gate endpoints only.
2. **No camera in v1.** Scanning QR codes requires the Android camera permission, which the app deliberately blocks and which the published privacy policy and Play data-safety form state is not used. Phase A therefore uses short typed codes. QR scanning needs a separate privacy, store-listing and permission change and is deferred.
3. **No GPS, face or biometric capture**, as the brief requires.
4. **Offline guard entry is deferred.** If added, locally queued entries must be visibly distinct from server-confirmed ones.
